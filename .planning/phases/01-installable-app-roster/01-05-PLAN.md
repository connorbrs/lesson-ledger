## Flagged assumptions (no silent drops)

- **Delete is a second row, not a trailing button.** A row already holds a name (wraps to 2 lines) and a fixed trailing Restore action. Two trailing actions ("Restore Student" plus "Delete Student") would leave about 75 px for the name at 375 px width. A full-width destructive row directly beneath the record reuses the existing `Row` tone `destructive`, the 44 px touch target and the `.row` separators, and needs no CSS (styles.css stays unchanged).
- **The blocked-family text is a note row, not a Group footer.** `Group` footers are per group and the Families group lists several families, so the text must sit under its own family. It is one non-interactive row using the existing `row-label row-sub` classes (13 px, text-secondary), the same classes this screen already uses for "Restore the family first". The copy is the one the user specified, shown in the UI-SPEC as a "Label footer"-size note.
- **Edge not covered by the user's wording (surfaced, not planned):** an archived family whose students are all still active (archiving a family does not touch its students) has no archived student to delete, so it shows the same note with no student listed under Archived. The way out is Restore Family, then archive or delete the students from People. If the user wants a second wording for this case it is a one-string follow-up; this plan implements the wording the user gave.
- **Student with sessions:** no Delete row and no note (the Student sheet already shows "This has sessions, so it can only be archived."). Phase 1 has no session UI, so this is reachable only through the tests; the Archived-row wording for history belongs to Phase 2.
- **No DOM test environment exists** (vitest runs in node, no jsdom). UI behaviour is proved by the type check and build, the bundle string check and the end-of-phase human checks; adding a DOM test stack is out of scope.
