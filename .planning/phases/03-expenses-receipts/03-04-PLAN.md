**As a** private instructor, **I want to** attach expenses and receipt photos to sessions, **so that** families see what I paid. (Phase 3 goal from ROADMAP.md; this plan delivers receipt photos: capture or pick, downscale, thumbnails, the viewer and removal.)

<objective>
Let the instructor attach zero or more receipt photos to an expense from the camera or the photo library, see them as thumbnails (still there after a relaunch and offline), open one full size, and remove one, with every photo downscaled to a small JPEG before it is staged and written with the session in one transaction.

Purpose: EXP-02 and EXP-03, plus the photo half of EXP-05 (removing a photo leaves no orphan). The pixel path (EXIF orientation, HEIC decode, canvas memory) is only checkable on the phone, so the pipeline is a pure sequence over an injected environment that tests drive with fakes, and the real browser environment is isolated in one function the device check can retune.
Output: photo constants and resize math, the sequential pipeline with tests, the staging Map and thumbnail hook, the Receipts group, and the Receipt viewer.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User-chosen image file to decoder | An arbitrary file (camera, library, Choose File) crosses into the browser's image decoder and a canvas |
| Staged Blob to IndexedDB | Only the re-encoded JPEG may be stored |
| Stored Blob to object URL to DOM | Receipts may show faces, names, addresses and account digits |

## STRIDE Threat Register

Threat IDs continue after plan 03-03 (T-03-05 and T-03-06). `T-03-SC` is reserved and kept by every plan.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-07 | Denial of service | Photo pipeline memory and time | medium | mitigate | 25 MB source cap checked before decode, 50 MP pixel cap checked after decode, strictly one photo at a time, canvas sized to 0 and decode released in a finally, 10 MB stored cap; tests prove sequencing and release on every path; about 20 receipts checked on the phone in plan 03-05 |
| T-03-08 | Information disclosure | Photo metadata (EXIF, GPS) retained in stored receipts | medium | mitigate | Every stored photo is a canvas re-encode, which carries no source metadata block; the app never stores the original file. The re-encode behavior is a platform assumption and is observed in the plan 03-05 device check |
| T-03-09 | Denial of service | Object URL and decode leaks | low | mitigate | One URL per photo per mount created only in an effect and revoked in its cleanup, in one file (grep gate: only receiptPhotos.ts creates URLs in the UI); image src cleared on release |
| T-03-10 | Tampering | A non-image or mislabelled file stored as a receipt | high | mitigate | Nothing the user picked is stored: bytes come from the canvas encoder; the encoded result must be type image/jpeg, non-empty and start with FF D8 FF; the data layer from plan 03-01 also rejects any staged Blob whose type is not image/jpeg; an undecodable file never reaches storage |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is added: no HEIC decoder, no image library (D-06); the dependencies check in task 1 acceptance proves package.json runtime dependencies are exactly dexie and preact |
