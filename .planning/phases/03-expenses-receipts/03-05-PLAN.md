## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Picked backup file to restore | An arbitrary file, including a hand-edited or hostile one with base64 images, may replace all data |
| App to share sheet or download | Families' names, expenses and receipt photos leave the app in one plaintext file |
| Restore transaction to IndexedDB | A failure part-way must not leave partial data or lose receipts |

| T-03-11 | Tampering | Crafted photo or expense entries in a backup (non-JPEG payload, bad base64, dangling references, wrong shares, hostile keys) | high | mitigate | parseBackup validates type, range, reference, set-equality of shares, exact sums, base64 charset and length, JPEG prefix, decoded size and dimensions for every entry before any write; rows are rebuilt from whitelisted fields; table-driven rejection tests assert the database is unchanged |
| T-03-12 | Denial of service | Oversized backup or oversize photo entry | high | mitigate | 150 MB cap judged by file size before the file is read; per-photo decoded cap of 10 MB checked on string length before character scanning; export pre-checks projected size so the app never writes a file it would refuse; the 140 MB and 151 MB device check exercises the limits |
| T-03-13 | Tampering | Non-atomic restore leaving partial data or wiping receipts (WR-02) | high | mitigate | Every photo is decoded to a Blob before the transaction; one rw transaction clears and bulk-adds every data table including expenses and attachments and sets lastBackupAt; injected duplicate-id and bad-base64 tests prove nothing changes; the existing two-step confirm alert is kept |
| T-03-14 | Tampering | Export that writes a file restore refuses (breaks the one-way contract) | high | mitigate | Size pre-check and final File-size check refuse above the cap; a test serializes a receipts export and parses it back; stored photos are already restricted to JPEG with the magic prefix and a size cap by plan 03-04 |
